# CSV 项目提交标准

交付可构建的修复工程、清晰的定位与验证及修复提交历史、按项目模板填写的报告，以及可追溯的测试和性能证据。

## 范围与版本

- 先核对用户指定的 Part、版本和验收项。Part A 不自动实现 importStreaming 或 shutdown。
- 保留初始基线与审查提交。按定位、回归验证、实现修复、最终验收分阶段提交，不改写已发布历史。
- 只有用户授权发布时才推送并创建版本标签；标签对应已完成验收的提交，不覆盖已有标签。
- 尊重本仓库的发布范围：data、tests、third_party、Cursor 配置与旧机器脚本留在本地，不因交付自动强制加入 Git。上传报告和小型证据，不上传 1 GB 样本或构建产物。

## 修复与回归

- 逐条建立复现输入、预期和实际结果，再修改实现；不要通过减弱断言消除失败。
- 验证文件尾无换行、解析器重入、跳过坏行、编码与分隔符、严格转换、内存上限、64 位行号、双引号转义和混合行尾。
- GBK 的合法尾字节不含逗号 0x2C。自定义分隔符可用 0x7C 构造真实冲突；非法编码应明确报错。CRLF 验收数据要实际包含 CR，字段中的 CR 用明确引用表达。
- 在现有 FieldRule 范围框架内修复边界，不另建一套校验框架。类型转换必须让调用方区分非法输入与合法零。
- Part A 对应的 DISABLED 用例应启用，ErrorLimit 不能以 GTEST_SKIP 或未打开输入的空结果算通过。Part B 用例如仍禁用，应单独标明。
- 使用 CMake Tools 构建和 CTest 工具测试；确认实际测试的源码目录、二进制配置和编译器标志。不要把工具选错项目或缺少样本导致的失败当成业务复现。
- 同一组功能断言在 Debug /Od 和 Release /O2 下通过。启用 ASan 时检查选项兼容性、运行相同内存相关断言，保存零错误输出；未启用或未执行必须明确记录。

## 证据

- 将证据保存在 docs/evidence/版本号 中，记录提交、配置、命令参数、输入大小和校验值、退出码及测试计数。
- csvp_bench 前后对比必须使用相同数据、配置和重复次数。已超时的基线只能作为下界或未完成记录，不能伪造完成耗时。
- sample_1gb.csv 必须实际测量进程内存；报告峰值工作集、峰值私有内存、采样周期、耗时、成功及跳过行数，并说明操作系统缓存与进程内存不同。
- 内存限制同时考虑错误数量和详情字节；报告中只留少量错误样本不等于运行时有上限。
- 有破坏性可能的复现仅使用临时副本，例如报告与输入路径相同；不覆盖真实样本。

## 报告与交付

- 按 [报告模板](../../../docs/REPORT_TEMPLATE.md) 的结构填写版本报告，保留未实施部分并注明范围，不伪称完成。
- 每个缺陷给出复现步骤、根因、具体修复、测试证据链接；把静态风险与实际运行结果分开。
- 附关键测试日志、ASan 输出（启用时）、前后压测数据、1 GB 内存实测和 git log 摘要。
- 交付前核对工作区与暂存区、排除本地资料、检查报告链接，确认推送分支与标签的远程哈希。
